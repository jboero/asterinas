Asterinas · ARMv7-A (32-bit) port

QEMU machine-type compatibility

Every one of qemu-system-arm's 98 machine types, booted with the same 32-bit Asterinas kernel and a C-free initramfs. A pass means the kernel reached userspace and the /init program ran a real write/exit syscall. The port targets the paravirtual virt board with a cortex-a15 CPU (LPAE, GICv2, the ARMv7 generic timer). Boards were probed with that CPU forced on, exactly as the AArch64 matrix forced cortex-a72.

32-bit boards now accept the image. On the AArch64 matrix these same ARMv7 SoCs were rejected outright (“incompatible architecture”). Here the 32-bit kernel loads on 18 of them — incl. vexpress-a15, mcimx6ul-evk and mcimx7d-sabre (Cortex-A7/A15, LPAE) and raspi2b — they just lack a PL011 UART at virt's 0x0900_0000, so nothing reaches ttyS0. Those are the real next-target candidates. The 4 virt-5.0…virt-6.0 rows go further still: the kernel fully boots, then faults on a device MMIO address the pre-6.1 virt memory map places elsewhere. The rest are Cortex-M microcontrollers (no MMU) or pre-ARMv7 / pre-LPAE cores that cannot run the kernel.

Base run: -cpu cortex-a15 -m 512M -smp 1 -kernel <elf> with the initramfs via -device loader. Boards that demand a core count or a fixed RAM size were re-run with it (shown per row). A machine outside virt fails because it is different hardware — a Cortex-M microcontroller, a pre-ARMv7 or pre-LPAE core, a fixed RAM size, or a distinct SoC memory map with no PL011 at 0x0900_0000 — not because of a missing kernel capability. This mirrors how the upstream x86 / RISC-V / LoongArch ports each target one board.
